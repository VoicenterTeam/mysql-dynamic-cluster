# Changelog

## 5.0.0 (unreleased)

### Breaking changes

- **`cluster.query()` rejects with the mysql2 error itself** (#88). The error of the node tried last keeps its own `message`, `code`, `errno`, `sqlState`, `sqlMessage`, `sql` and `fatal`, and gets `nodeId`. The errors of the nodes tried before it are in `errors`, as `{ nodeId, error }`. The joined `Pool: <name>; Error: Query error: <message>` text is gone: read `code` and `errno` in place of the message. An error with an `errors` array of its own, such as Node's `AggregateError` of a host name with several addresses, keeps it and gets no list. The `All pools have error` log line is gone; each attempt is still logged.
- **The error of `query()` carries `sql`**, the statement as mysql2 sent it, with the values `query()` wrote into it. The 4.x error did not. An app that logs or ships errors whole now ships those values too, so it should drop `sql` first.
- **No valid node: `code: 'MDC_NO_NODE_AVAILABLE'`** on the error of `query()`, as `getConnection()` already had. The message stays `There is no pool that satisfies the parameters`, without the `Error: ` in front of it.
- **The `mysql_dynamic_cluster.query.duration` metric of a failed query** now has the real `error.type` and `db.response.status_code`, not `_OTHER`.
- **An error the app handed `failWaiting()`** now reaches `query()` callers as that object itself, with `nodeId` and `errors` set on it, as `getConnection()` callers already got it with `nodeId`.
- **`errorRetryCount: 0`** now tries one node. Before, the query tried none and rejected with an empty error.
- **`cluster.query()` tries another node only when the statement cannot have run on the one before** (#87): it was never sent (no connection came, or the change of database failed or timed out), or the node answered 1047, not ready. An error reply, a timeout or a connection lost after the statement went out ends the call. Before, the next node got the statement too, and one call could write twice. A refused login (errno 1045, 1698, 1044, 3118, 3955 or 1130) is not tried on another node either: Galera replicates the accounts, so the next node refuses it too, and each login counts toward a lockout. No setting brings the old retry back. `errorRetryCount` and `maxRetry` still cap how many nodes a call may try. The new query option `retryNotReady: false` stops the try after 1047, for a procedure that commits part of its work. A throw of the hashing update after the statement passed is logged as a warning and the call resolves, where before the statement went to the next node. The warning before stale Redis data now reads `The query failed. Use old data from Redis`.
- **The error of `query()` carries `sent`**, and so does each error in its `errors`: `false` when the statement never went to the server, `true` once it was handed to the connection. A frozen error goes without it. For a node without a `healthCheck` block, the check asks through the same pool path, so an error of the pool that a `pool_check_failed` listener gets carries `sent` too. The check's own `Status check timeout` does not.

### Added

- **A `signal` query option** (#89): an `AbortSignal` that cancels a `cluster.query()`. The call rejects with the reason of the signal as it is, without `nodeId`, `errors` or `sent` on it. An abort while the request waits for a connection takes it out of the queue of the pool, as `getConnection({ signal })` does. An abort during the change of database or the statement destroys that connection with its socket and never releases it, and the pool opens a new one in its place. A statement the server already got may still finish. No other node is tried after an abort, stale Redis data is not served, and passive health is not told. A signal that is already aborted rejects at once, before the service-name lookup, Redis and any node. A value that is not an `AbortSignal` rejects with a `TypeError`. The aborted call is recorded as a failed query with the reason as its error. No listener stays on the signal once the call settled. `multiStatementQuery()` reads no signal.

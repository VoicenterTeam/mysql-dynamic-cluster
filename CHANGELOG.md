# Changelog

## 4.2.0 (2026-11-25)

The same code as 4.2.0-rc.4, which vc-dal tested on its unit and MySQL contract suites and a three-node Galera rig.

### Added

- **`onStep`, a query option called as an attempt enters each step** (#140).
  - `query()` and `execute()` call `onStep(step, nodeId)` synchronously each time an attempt enters `queue`, `probe`, `prepare` or `statement`, and only when the step or the node changes.
  - `statement` comes right after mysql2 took the statement, so from then on the statement counts as sent.
  - When the call settles, the last `onStep` equals the step and node that `onTiming` reports. So an app knows at the moment it calls `abort()` whether the statement may have been sent, with no wait for `onTiming`.
  - After a failed probe, the new request to mysql2 is `queue` again. `statement` on one node followed by `queue` on another means that node answered 1047 and did not run the statement.
  - It follows the rules of `onTiming`. A value that is not a function rejects with a `TypeError` and `sent: false` before any node, and `null` counts as no option. A throw or a rejected promise is logged at most once per call and changes nothing. An `abort()` from inside it acts as an abort at that moment.
  - It is not called for a Redis hit, a refusal before any node, or after the call settled. `getConnection()` and `multiStatementQuery()` do not take it.
  - Without the option, nothing is allocated per attempt.

### Changed

- **A node that goes down fails the requests that wait for its connections** (#98).
  - When a node goes from valid to down, for any reason and in both check modes, its pool fails every request waiting for one of its connections. Each request gets its own error: `code: 'MDC_NODE_DOWN'`, `sent: false`, `nodeId`, and a message that names the host.
  - Before, those requests waited in mysql2's queue behind connection attempts of up to `connectTimeout` each, up to minutes.
  - `query()` and `execute()` move such an attempt to the next node under the retry rule, and reject with that error when no try is left. `getConnection()` rejects with it.
  - The legacy check's own status query that waits there is not failed.
  - The error does not count for passive health. `error.type` of the metrics can now be `MDC_NODE_DOWN`.
  - One info line names the host and how many requests were failed, when at least one was.
  - These are not touched: requests that already hold a connection, logins already running, and requests that arrive after the down. So the worst wait left is one connect timeout. A retry skips a node that already went down (#151, below).
  - `failWaiting()` is unchanged.
- **Each cluster has its own logger and its own metrics `clusterName`** (#86).
  - Each cluster logs through the `logger` and `logs.level` of its own settings, in every part of it: the cluster, its pools, health checks, validators, load factors, borrows, sessions, check connections, cluster hashing and service names.
  - Each cluster stamps its own `clusterName` on every metric it records, including the connection metrics and node gauges read at collection.
  - A second `createPoolCluster` in the same process no longer changes the first cluster's logger, level or metrics name.
  - Still shared: the event emitter, the Redis client with its key prefix (any cluster's `disconnect()` disconnects it), `config.current`, and the module logger. The shared parts log through the module logger, which gets the settings of the last `createPoolCluster`. See `docs/architecture.md#singletons`.
  - Calling `Logger.init` or `Metrics.init` directly after `createPoolCluster` now changes only those shared parts.
  - A one-cluster app sees the same log lines and metric points as before. Exports, settings, event payloads, and metric names and attributes are unchanged.
  - When `createPoolCluster` is called again, the warning says what the earlier cluster keeps: "createPoolCluster was called again: the earlier cluster keeps its own hosts, logger and metrics name; the Redis client and the events are shared with the new one". The prefix is the same as before.

### Fixed

- **A retry skips the nodes that are no longer valid** (#151).
  - `query()` and `execute()` take their list of nodes when the call starts. From the second attempt on, a node that is no longer valid when its turn comes is skipped. It is not asked, it gives no step and no metric record, and one debug line names it.
  - A skipped node does not count as a try. When no node is left, the call rejects with the error of the last node tried, as before.
  - The first attempt, the cluster-hashing order and the retry rule are unchanged.
  - So a call that got `MDC_NODE_DOWN` no longer joins the queue of another node that went down while it waited.
  - "Retrying query..." is logged only when a node is asked.

## 4.1.1 (2026-11-24)

The same code as 4.1.1-rc.2, which vc-dal tested on its unit and MySQL contract suites and a three-node Galera rig.

### Fixed

- **`query()` refuses values that a `/*+ */` or `/*!NNNNN */` comment can turn into SQL** (#134). A server that skips such a comment ends it at a `*/`, also one written by a value, and takes a `/*` in it as a nested comment. A rig with MySQL 8.0.42 ran a value written there as SQL. `query()` now rejects with `code: 'MDC_UNSAFE_COMMENT_VALUE'`, before any node is asked, in two cases. In the first, the statement holds `/*+`, MariaDB's `/*M!`, or a `/*!` followed by a version or by a placeholder that can write one, and its values add a `/*` or a `*/`. In the second, values are written into a statement where such a comment holds a `/*`, or where a string, identifier or comment opens inside such a comment and runs past its end, so the server and sql-escaper read the rest differently. That case has its own message, which points to `execute()`. Balanced quotes in a hint (`SET_VAR(sql_mode = 'X')`), `MAX_EXECUTION_TIME(:ms)`, `/*! */` alone, statements without such a comment and `execute()` are unchanged. Two harmless shapes are refused too: an opener inside a string with no `*/` after it, such as `LIKE '%/*+%'`, and a `/*` nested in a hint. Use `execute()` for them. `query()` also writes the values into the text once, before it waits for anything. So a `toSqlString()` runs once, a later change to the values does not reach the text, and a value that throws while it is written rejects with its own error before the service-name lookup and before `MDC_NO_NODE_AVAILABLE`.
- **The log line of a failed attempt names the error** (#106). It carries the `code` and the `errno`. An `AggregateError`, `undefined` or `null` is named, where the line used to end at the colon.
- **An error whose `errors`, `code` or `errno` throws when it is read no longer replaces the error of the call** (#106). The call is recorded, and its query-duration point is still written.
- **A throw while values are written into the text is recorded as a failed query** (#48), also a throw while the placeholders of an object of values are checked, and also on the stale-cache path.
- **A pinned node that is not valid is left out** (#43). The node a service is pinned to is never the first attempt when it is not valid. Cluster hashing builds its schema on the first valid node.
- **`connect()` of a cluster** (#61):
  - A cluster without hosts resolves at once.
  - `connect()` rejects with a string for any rejection of a pool, and `ready` and `firstReady` resolve, also for a value that cannot be made text.
  - A second `connect()` without `disconnect()` settles. It settles within one tick when the cluster is connected, and otherwise with the connect that is running. It keeps its own `ready` and `firstReady`.
  - A `connect()` that `disconnect()` came after no longer marks the cluster connected, starts hashing, or emits `connected` or `hashing_created` after `disconnected`, also when `disconnect()` comes while the hashing runs.
  - Overlapping connects of cluster hashing share one run. A run that `disconnect()` stopped no longer interleaves its schema statements with the next run or marks hashing connected.
  - A pool no longer emits `pool_connected` after `pool_disconnected` when a `disconnect()` or a later `connect()` comes during the health check of its `connect()`.
- **Listeners that throw** (#61). A `connection`, `acquire`, `release`, `pool_connected` or `pool_disconnected` listener that throws is logged at warn. It no longer loses a connection, leaves `getConnection()` or `query()` pending, rejects `connect()`, or cuts `cluster.disconnect()` short. Such a listener also no longer keeps the listeners after it from the event: the first throw still reaches the code that emitted the event, and later ones are logged at warn with the name of the event. A `pool_check_failed` listener that throws a value whose stack cannot be read no longer rejects the health check.
- **`failWaiting()` logs one info line** with the host and how many requests it failed (#61).
- **The idle reaper** (#102) no longer logs a false "an idle connection failed its ping and was closed" for a connection its age rule closed. On a node without a `healthCheck` block, it forgets and drops idle connections that mysql2 took out of its pool.
- **A health check no longer asks again on a new connection** when a check connection that was still logging in is lost (#97). A check that asks on a new connection writes one debug line with how that connection ended.
- **One warn per host about its id** (#71): an id that is negative, not an integer, shared with another host, or above 127 with `useClusterHashing`. Ids the cluster gave are included, and the warning about a replaced id 0 is merged into it.

### Changed

- **The refusals of `query()` and `execute()` before any node carry `sent: false`.** These are the `TypeError`s of the options and of the `execute()` values, `MDC_QUOTED_PLACEHOLDER`, `MDC_UNSAFE_COMMENT_VALUE` and `MDC_NO_NODE_AVAILABLE`, so a caller can tell that the statement never went out without knowing each code. The reason of an aborted signal and an error the app's own values throw stay as they are. The errors of `getConnection()` carry no `sent`.
- **The package no longer ships source maps** (#38). `sourceMap` is off in `tsconfig.build.json`, so the tarball holds 78 files instead of 112.

## 4.1.0 (2026-11-23)

The same code as 4.1.0-rc.1, which vc-dal tested on its unit and MySQL contract suites and a three-node Galera rig.

### Added

- **`onTiming`, a query option that tells where the time of a call went** (#122). `query()` and `execute()` call it once when the call settles, before its promise does, with `step`, `queuedMs` and `nodeId`. `step` is where the last attempt ended: `queue` (waiting for a connection of the pool, in mysql2's queue or while a new connection opens), `probe` (the ping of an idle connection), `prepare` (the reset, `USE` or `DO 0` before the statement) or `statement` (the statement was sent, also for a call that resolved). `queuedMs` is the time the call waited for a connection, summed over every node it tried, in milliseconds with a fraction. `nodeId` is the node of the last attempt. So an app can tell a call that waited for a busy pool from one that was slow on its node. It is not called for a Redis hit or a call refused before any node. A throw in it, or the rejection of a promise it returns, is logged once and changes nothing, and the error and the reason of the signal stay as they are. `null` counts as no option, as for `signal`. The package exports `IQueryTiming` and `QueryStep` as types. Any other value that is not a function rejects with a `TypeError` before any node. `multiStatementQuery()` and `getConnection()` do not take it.
- **The step and the wait of each attempt as metrics** (#122). Each attempt of `Pool.query` records the step it ended in as the attribute `mysql_dynamic_cluster.attempt.step` of `mysql_dynamic_cluster.operation.duration`, and the time it waited for a connection in the new histogram `mysql_dynamic_cluster.connection.wait_time`: seconds, the buckets of the other durations, and the attributes that name the node. The attempts of `query()` and `execute()` and the status query of the legacy health check record both. `multiStatementQuery()` and the check of a node with a `healthCheck` block record neither. The new attribute splits each existing `mysql_dynamic_cluster.operation.duration` series by step; sums over the other attributes are unchanged.

## 4.0.1 (2026-11-23)

The same code as 4.0.1-rc.1, which vc-dal tested on its unit and MySQL contract suites and a three-node Galera rig.

### Fixed

- **A `:name` inside quotes or backticks is refused** (#131). 4.0.0 replaced a `:name` of the object wherever it stood, inside a string literal or backticks too, and the quotes of the escaped value closed the literal: `name = ':n'` with ` OR 1=1 OR ` sent `name = '' OR 1=1 OR ''`. Now `query()` rejects such a call with `code: 'MDC_QUOTED_PLACEHOLDER'` before any node is asked, when the object has that key. The text is read as sql-escaper reads it for a `?`. A `:name` inside a comment is left as text, where 4.0.0 replaced it too. In 4.0.0 a value that held `*/` could also close a `/* */` comment around a `:name`. The `:name` now stays text there. One inside `/*! */` or `/*+ */` is still replaced: it is treated as code, as sql-escaper treats a `?` there. MySQL reads `/*+ */` as a hint only right after the first keyword of `SELECT`, `INSERT`, `REPLACE`, `UPDATE` or `DELETE`, and skips `/*!NNNNN */` when `NNNNN` is above its version. Read as a plain comment, it ends at the first `*/`, also one inside a value. So keep values out of comments. Array and string values and `execute()` are not affected. An app writes `id = :id`, not `id = ':id'`. A quoted number such as `id = ':id'` with `{ id: 5 }` worked by accident in 4.0.0, as `id = '5'`, and now fails.

## 4.0.0 (2026-11-23)

The same code as 4.0.0-rc.2, which vc-dal tested on its unit and MySQL contract suites and a three-node Galera rig.

For an app that upgrades from 3.2.2. The table "Migrating from 3.x" in `docs/configuration.md` lists every setting that moved.

### Breaking changes

- **Settings come only from the object passed to `createPoolCluster`, and they are validated** (#17). The library no longer loads `.env` and no longer reads `MYSQL_*`, `LOGGER_*`, `LOG_AMQP_*` or `MYSQL_CONFIG_FILES`. A strict zod schema checks the settings, and `createPoolCluster` throws one error that names every unknown key and every wrong type. A numeric string such as `port: process.env.DB_PORT` is refused, and so is a host without `host`. `logs.level` must be one of the lowercase level names. `showMetricKeys` is removed. The Redis settings key is `redis`, as it always was at runtime: `redisSettings` in the TypeScript interface was ignored. The defaults are unchanged.
- **winston and the AMQP log transport are gone** (#15). `createPoolCluster` takes an optional `logger` with `debug`, `info`, `warn` and `error`. Without one, messages go to the console, one line each. `logs.level` filters before the call, and a logger that throws never fails a query. `logs.output` and the `amqp_logs` settings are removed: an app that ships logs over AMQP builds its own logger and passes it in.
- **Metrics go through OpenTelemetry, and `@pm2/io` is gone** (#14, #22). `@opentelemetry/api` ^1.7.0 is a required peer dependency. The package brings no SDK and no exporter: without a `MeterProvider` the app registers, every record is a no-op. The pm2 metrics are gone, and `docs/subsystems/metrics.md` maps them to the new instruments: the histograms `mysql_dynamic_cluster.operation.duration`, `mysql_dynamic_cluster.query.duration`, `mysql_dynamic_cluster.cache.lookup.duration` and `mysql_dynamic_cluster.health_check.duration`, the counters `mysql_dynamic_cluster.connection.count`, `mysql_dynamic_cluster.connection.pending_requests` and `mysql_dynamic_cluster.connection.limit`, and the gauges `mysql_dynamic_cluster.node.valid` and `mysql_dynamic_cluster.node.load_score`. Requiring the package no longer installs the `unhandledRejection` and `uncaughtException` listeners of `@pm2/io`, whose rejection handler only printed, so an app exits on an unhandled rejection again.
- **`cluster.query()` rejects with the mysql2 error itself** (#88). The error of the node tried last keeps its own `message`, `code`, `errno`, `sqlState`, `sqlMessage`, `sql` and `fatal`, and gets `nodeId`. The errors of the nodes tried before it are in `errors`, as `{ nodeId, error }`. The joined `Pool: <name>; Error: Query error: <message>` text is gone: read `code` and `errno` in place of the message. An error with an `errors` array of its own, such as Node's `AggregateError` of a host name with several addresses, keeps it and gets no list. The `All pools have error` log line is gone; each attempt is still logged.
- **The error of `query()` carries `sql`**, the statement as mysql2 sent it, with the values `query()` wrote into it. The 3.2.2 error did not. An app that logs or ships errors whole now ships those values too, so it should drop `sql` first.
- **No valid node: `code: 'MDC_NO_NODE_AVAILABLE'`** on the error of `query()`, as on the error of `getConnection()`. The message loses the `Error: ` that 3.2.2 put in front of it. It is now `There is no pool that satisfies the parameters`.
- **`errorRetryCount: 0`** now tries one node. Before, the query tried none and rejected with an empty error.
- **`queryTimeout` must be 0 to 2147483647 ms.** Strict validation refuses a negative `queryTimeout` and one above 2147483647 ms, the longest wait a timer of Node takes, in `defaultPoolSettings` and on a host. A negative one fired at once and a longer one after 1 ms, so every statement timed out and its connection was destroyed. 0 still means no limit. A per-call `timeout` above 2147483647 ms is clamped to it for `query()`, `execute()` and `multiStatementQuery()`, and a negative `timeout` makes `query()` and `execute()` reject with a `TypeError` before any node is asked.
- **`cluster.query()` tries another node only when the statement cannot have run on the one before** (#87): it was never sent (no connection came, or the reset, the `USE` or the `DO 0` before it failed or timed out), or the node answered 1047, not ready. An error reply, a timeout or a connection lost after the statement went out ends the call. Before, the next node got the statement too, and one call could write twice. A refused login (errno 1045, 1698, 1044, 3118, 3955 or 1130) is not tried on another node either: Galera replicates the accounts, so the next node refuses it too, and each login counts toward a lockout. No setting brings the old retry back. `errorRetryCount` and `maxRetry` still cap how many nodes a call may try. The new query option `retryNotReady: false` stops the try after 1047, for a procedure that commits part of its work. A throw of the hashing update after the statement passed is logged as a warning and the call resolves, where before the statement went to the next node. The warning before stale Redis data now reads `The query failed. Use old data from Redis`.
- **No change of user before a query** (#90). `query()`, `multiStatementQuery()` and the health check sent a `COM_CHANGE_USER` before every statement, to switch the database. They now send `USE` only when the connection is on another database, so a query on the database of the pool is one command. The change of user also reset the whole session every time. Now a connection is reset (`COM_RESET_CONNECTION`) before it goes back to the pool only when it is dirty: the query failed, or a header of its reply says a transaction is open or autocommit is off. So every error reply, a duplicate key for one, now costs a reset, and that reset drops the session variables, user variables and prepared statements the connection held, also those `execute()` prepared. So session state a clean query leaves stays on the connection for the next query of the pool: user variables, session variables set with `SET`, named locks of `GET_LOCK()`, tables locked with `LOCK TABLES`, temporary tables and prepared statements. The change of user released all of them. A reset keeps the current database. It has a time limit of its own, the new pool setting `resetTimeout` (1000 ms by default): a reset that fails or runs out of time destroys the connection with its socket, and a connection the node answered 1047 on is destroyed with no reset, since such a node answers no reset. A connection an app took with `getConnection()` is reset at its `release()` (#93) and gets a `USE` before a query of the cluster uses it again. A pooled connection whose path was cut silently and that was used within `probeIdle` now fails under the statement, with `sent: true`, so the next node is not tried; before, the change of user met the reset first and the next node got the query. One idle longer than `probeIdle` fails its probe instead, and the query is answered on the next connection of the node (#93). On a Galera node outside the primary component a query now gets 1047 at once, where it waited for its timeout on a change of user that got no answer. The check of a node with a `healthCheck` block, on a connection of its own, sends a change of user before its status query.
- **A `USE` sent through `query()` stays on the connection when the server has `session_track_schema=OFF`** (#90): the pool sees it only by the session-state bit of the reply, so the next query of the pool on that connection runs in that database. Use the `database` query option instead.
- **The error of `query()` carries `sent`**, and so does each error in its `errors`: `false` when the statement never went to the server, `true` once it was handed to the connection. A frozen error goes without it. For a node without a `healthCheck` block, the check asks through the same pool path, so an error of the pool that a `pool_check_failed` listener gets carries `sent` too. The check's own `Status check timeout` does not.
- **Named values are always escaped** (#91). `query(sql, { name: value })` writes each value through sql-escaper's `escape` (the function mysql2 exports), as array and string values already were. In 3.2.2 each named value went into the text as it was. A service that relied on that must remove the quotes around its placeholders and move SQL fragments out of the values, see `docs/configuration.md`. The formatted SQL is the Redis key, so each such query misses the cache once.
- **`query()` refuses values in the text under `NO_BACKSLASH_ESCAPES`** (#91). When the last OK header on a connection had bit 512 set, a `query()` that wrote values into its text rejects with `code: 'MDC_UNSAFE_SQL_MODE'` and `sent: false` before the statement is sent, and no other node is tried. The connection goes back to the pool as it is. A query whose formatting left the text as it was, such as `query(sql, [])` or `query(sql, {})`, a query without values, and `execute()` are not affected. There is no setting. A connection learns the mode only from an OK header (the reply to a `SET`, `INSERT`, `UPDATE`, `USE` or `CALL`), never from rows, so the mode is unknown on a new connection, after every reset, and on a connection that only returned rows. Before a `query()` with values in its text on such a connection the pool sends one `DO 0` and reads the mode from its header, so the guard has no gap. That costs one `DO 0` per connection and per reset, only for calls that write values into the text: `execute()`, a query without values and `multiStatementQuery()` never send it. A `DO 0` that fails or runs out of the query's `timeout` fails the call with `sent: false`, so the next node may be tried. Under that mode `execute()` is the only safe way to send values. The package's own statements with values (the service-name lookup, `SP_NodeServiceUpdate`, `SP_NodeInsert` and the hashing schema checks) now go through `execute()`, so such a server does not stop them.
- **A connection is reset after `resetAfterStatements` replies** (#93), a new pool setting, 1000 by default, 1 at least: a connection goes back to the pool through a reset once it got that many replies since its last reset, so prepared statements a procedure left behind cannot pile up now that a clean connection goes back with no reset. The session state a clean query leaves on a connection (see #90 above) is dropped at that reset, every N replies, so no app may count on finding it. There is no value that turns the reset off.
- **Packets out of order: `code: 'MDC_PACKETS_OUT_OF_ORDER'`** (#94). mysql2 only warns when a reply comes with a wrong sequence number, and waits on, often until the timeout. While a statement of `query()` or `execute()` runs, during the probe, the reset and the `USE`, during the reset at the `release()` of a lent connection, and while an app holds a connection of `getConnection()`, the pool listens for that warning. The connection is destroyed with its socket, and the call rejects at once with `code: 'MDC_PACKETS_OUT_OF_ORDER'`, the numbers `expected` and `received`, `nodeId` and `sent: true`. A caller that got a timeout for such a reply (`PROTOCOL_SEQUENCE_TIMEOUT`) now gets this code, well before its timeout, so code that matched the timeout must match this code too. No other node is tried. During a probe it is a failed probe. On a lent connection the command of the app fails with the warning of mysql2. No `warn` listener stays on a connection after its call.

### Added

- **`cluster.getConnection(options)`** (#62, #74, #93): one connection of the valid node with the lowest load score that is not in `options.exclude`. It asks one node once and does not retry. It rejects with `code: 'MDC_NO_NODE_AVAILABLE'` when no node is left, and with the error of mysql2 plus `nodeId` when the node gives no connection. A `signal` option ends the wait for a connection and takes the request out of the queue of the pool. A connection that was idle longer than `probeIdle`, or one the reaper's ping is still out on, answers a ping before the app gets it; one that fails is destroyed and the next connection of the node is taken. The `release()` of the app resets the connection (`COM_RESET_CONNECTION`, bounded by `resetTimeout`, destroyed when the reset fails) before it goes back to the pool, so the next caller never gets a transaction, locks, temporary tables or session variables the app left. The connection counts as `used` until that reset is answered. A second `release()` does nothing, until a later `getConnection()` hands out the same connection again. While the app holds the connection, packets out of order destroy it (#94). See `docs/node-api.md`.
- **More of the node API** (#62, #66): `ready` resolves once every pool finished the first connect of the current `connect()` call, and `firstReady` when the first pool passed it, each with one result per node; neither rejects. `failWaiting(nodeId, error)` fails the requests that wait for a connection of one node and returns how many; a `query()` caller among them gets that error object itself, with `nodeId` and `errors` set on it. `getPoolStats()` counts the used, idle and waiting connections per node. `nodes()` lists the nodes as plain objects. A node and a result carry `checkError`, what the last health check failed with, reduced to `code`, `errno` and `sqlState`, so an app can see a refused login. The interfaces are exported as types.
- **A `healthCheck` block in the pool settings** (#76, #82, #96), in `defaultPoolSettings` and on a host, with `interval`, `timeout`, `fall`, `rise`, `authRetryInterval` and `passive`. A node with the block is checked every `interval` ms (5000 by default) on a connection of its own, so a busy pool does not fail its checks. It goes down after `fall` failed checks in a row (2 by default), and at once when a validator says no or the server refuses the login. It comes back after `rise` passes in a row (2 by default), and the first pass after `connect()` brings it up at once. After a refused login it waits `authRetryInterval`, by default the longer of 60000 ms and the interval, before it asks again. With `passive` (on by default) a call of the app that fails with an error of the network starts a check at once, and a refused connection takes the node down. The idle pooled connections of such a node get a ping, so a path that forgot them does not fail the next query. A node logs one warn when it goes down and one info when it comes back. A node without the block keeps the legacy check. See `docs/subsystems/health-and-scoring.md`.
- **The `pool_check_failed` event** (#23), with the error of each failed health check, so an app can tell a wrong password from a node that is down. The listener gets `[error, poolId]`, wrapped like every other payload.
- **The pool setting `flags`** (#33), in `defaultPoolSettings` and on a host: the `flags` connection option of mysql2, passed to `createPool` as it is. The flags of a host replace the default ones. A pool without `flags` logs in once before it creates its mysql2 pool, reads the greeting of the server, and turns `CLIENT_QUERY_ATTRIBUTES` off for a server older than 8.0.26 that announces it, since such a server never answers a prepared statement of mysql2 3.21.0 and later (#41).
- **A `signal` query option** (#89): an `AbortSignal` that cancels a `cluster.query()`. The call rejects with the reason of the signal as it is, without `nodeId`, `errors` or `sent` on it. An abort while the request waits for a connection takes it out of the queue of the pool, as `getConnection({ signal })` does. An abort during the reset, the `USE` or the statement destroys that connection with its socket and never releases it, and the pool opens a new one in its place. A statement the server already got may still finish. No other node is tried after an abort, stale Redis data is not served, and passive health is not told. A signal that is already aborted rejects at once, before the service-name lookup, Redis and any node. A value that is not an `AbortSignal` rejects with a `TypeError`. The aborted call is recorded as a failed query with the reason as its error. No listener stays on the signal once the call settled. `multiStatementQuery()` reads no signal.
- **`cluster.execute(sql, values, options)` and the query option `execute: true`** (#91): one statement with its values bound by the server, through mysql2's `execute()`. The values never become part of the text, so they are safe under any `sql_mode`. The same choice of node, retry rule, error, signal, metrics and passive health as `query()`. mysql2 prepares a statement once per connection and keeps it, so the second call of the same text on a connection is one command. The values must be an array, or none (`null` or `undefined`): anything else, or an array that holds `undefined`, a hole or a function, rejects with a `TypeError` before any node is asked. No Redis: an `execute` call neither reads nor writes it, whatever the `redis` option says. The `timeout` of the query covers the prepare too, which mysql2 does not time: on expiry the connection is destroyed. A statement runs in the database it was prepared in, so the pool closes the statements of a connection before a `USE` of another database (a `USE` back to the database they were prepared in keeps them) and before it lends the connection with `getConnection()`. `query()` without the option still writes its values into the text.
- **A probe of an idle connection before it is lent** (#93), for `query()`, `execute()`, `multiStatementQuery()` and `getConnection()`: a connection idle longer than the new pool setting `probeIdle` (1000 ms by default) gets a `COM_PING` first, within `probeTimeout` (1000 ms by default). An answered ping of the timer that closes idle connections counts as use. A ping of that timer still out is waited for within `probeTimeout`, not doubled, whether or not the connection was idle longer than `probeIdle`: no answer in that time is a failed probe. A probe that fails or gets no answer destroys the connection with its socket, passive health hears of a lost connection, and the next connection of the node is taken, at most `connectionLimit + 1` tries; a new connection needs no probe. The statement counts as not sent, so with every connection failing `cluster.query()` tries the next node. The probes of a node run one after another, and the `timeout` of the query does not cover them or the login of a new connection: a node whose idle connections all go unanswered costs about `connectionLimit × probeTimeout` plus one mysql2 `connectTimeout` (20 s with a limit of 10 and the defaults) before the next node is tried. On a node with a `healthCheck` block the borrow stops sooner, with `sent: false`, at the first failed probe after health gave the node up: a failed probe tells passive health of a lost connection, which starts a check, and that check takes the node down when it fails, within the block's `timeout` (5 s by default, so after about 6 to 7 probes). A node on the legacy check, the default without a block, has no passive health and keeps about the whole worst case. A connection used within `probeIdle` and a new one are lent as they are. The health check of a node without a `healthCheck` block is never probed. A path that forgot an idle connection now costs a ping, not a query.
- **The pool setting `maxPreparedStatements`** (#91), 100 by default: how many statements of `execute()` mysql2 keeps prepared per connection; past it the one used longest ago is closed. The server counts every statement of every client against `max_prepared_stmt_count` (16382 by default), so keep `processes × connectionLimit × maxPreparedStatements` per node below it.
- **A warning when a host loses its id 0** (#29). A host with id 0 next to hosts with other ids still gets a generated id, as before. The warn log names the host, its port and the id the node got.

### Fixed

- **A lost or dropped connection no longer keeps the process alive until its timeout** (#120). The pool handed its `timeout` to mysql2, which clears the timer of that option only when the command ends, not when the connection is lost or destroyed. So a command still out on such a connection kept a timer that held the process open until it fired, up to `queryTimeout` (120 s by default), and an app that then ran `disconnect()` waited that long to exit. The pool now bounds each of its commands with a timer of its own, unref'd and cleared at the reply, at the drop of the connection and at a throw of mysql2, and hands mysql2 no `timeout`. A timeout still fails with the error mysql2 gives (`Query inactivity timeout`, `code` and `errorno` `PROTOCOL_SEQUENCE_TIMEOUT`), a bound statement of `execute()` with the package's own error of that code, and the connection is destroyed. `timeout: 0`, or none, is still no limit.
- **A connection the pool gives up on is closed with its socket.** mysql2's `destroy()` only ends the writing side, so on a cut path the socket stayed open until TCP gave up and kept the process alive after `disconnect()`. A broken connection, one past its age, and one whose ping, reset or statement timed out are now destroyed with their socket.
- **The health checks run again after `disconnect()` and `connect()`** (#57). The check timer of a pool, and the one of cluster hashing, stayed off for good. A check still out from before the reconnect changes nothing when it ends. Two `connect()` calls without a `disconnect()` no longer run two check loops, and no longer leave a second idle timer running that kept the process from exiting (#82).
- **The service name of a query is a bound value** (#46). The lookup of a service id put the `serviceName` option between quotes into the SQL text.
- **The shipped declarations compile in more TypeScript setups** (#28, #36). `@types/ioredis` is a dependency now, not a devDependency, so an app with `skipLibCheck` off no longer fails with TS7016 inside `SettingsInterfaces.d.ts`. The mysql2 types come from the package root, not from `mysql2/typings/mysql`, which an app on `node16` or `bundler` resolution could not resolve.
- **A `?` inside a `"..."` string or a `#` comment no longer takes a value** (#121). `query()` wrote array values into the text with mysql2's `format()`, which is sql-escaper's. mysql2 3.24 allows sql-escaper 1.5.x, which replaced such a `?` as well: every value after it moved one place, and the last `?` stayed in the SQL. The package now depends on `sql-escaper ^1.6.0` and imports `format()` and `escape()` from it, called with mysql2's arguments: `query()` writes the text mysql2's `format()` writes with the same copy, and leaves such a `?` alone also when an app pins an older sql-escaper itself. npm usually resolves the fixed copy for mysql2 too: in a consumer whose lockfile held 1.5.2 through mysql2, installing the package moved that copy to the newest 1.x (1.9.1 when checked). An app that depends on a sql-escaper below 1.6 itself keeps that copy for mysql2, so mysql2's own `format()` and `escape()`, called by the app directly, still behave as 1.5.x there. `docs/subsystems/cluster.md` and the README now say what values do in the text: `??` is an identifier, a plain object after `SET` becomes `` `key` = value `` pairs, an object with `toSqlString()` is written raw, and only `execute()` keeps values out of the text.
